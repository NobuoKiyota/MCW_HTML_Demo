# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`ShooterCocos` is a Cocos Creator **3.8.8** vertical-shooter game, written in TypeScript. It is a port of an earlier vanilla-JS prototype that still lives at the repo root (`../js/shooter/engine.js`, `gridManager.js`, `missionManager.js`, etc.) — physics/scoring constants in this project are intentionally kept numerically consistent with that prototype (see comments like "similar to engine.js" in `GameManager.ts`).

The git repository root is one level up (`F:\ITANHTMl`), which also contains an unrelated portfolio web app, Blockbench/Cubase/Gimp asset-authoring folders, and `game_balance.xlsm` — the Excel workbook that `assets/scripts/GameBalanceData.ts` is auto-generated from. Do not hand-edit `GameBalanceData.ts`; regenerate it from the workbook.

## Commands

There is no npm/CLI build, lint, or test pipeline — `package.json` only contains editor metadata (no `node_modules`, no scripts). All building, running, and verification happens inside the **Cocos Creator 3.8.8** editor:

- Open the project via Cocos Creator Dashboard → this folder (`cocos_project`).
- Use the editor's Preview/Play button to run `scene-Main` (the project's only scene).
- Verify changes by reading the Console output — nearly every manager class logs verbosely with a `[ClassName]` prefix specifically so behavior can be traced without a debugger (e.g. `[GameManager]`, `[UIManager]`, `[SoundManager]`, `[GameDatabase]`).
- `tsconfig.json` extends `./temp/tsconfig.cocos.json`, which is auto-generated by the editor on open — never edit `temp/` by hand.

## Critical rules (hard-won, see `../docs/260224_PostMortem.md`)

- **Never write scripts that directly edit `.scene` or `.prefab` JSON files.** These files use fragile `__id__` cross-reference graphs; a partial rewrite (as attempted by a since-deleted `fix_prefabs.py`) previously corrupted prefabs and destroyed root nodes. Leftover *read-only* diagnostic scripts (`assets/scripts/mask_scanner.py`, `scene_repair.py`, `disable_masks.py`, `check_csv.py`) exist from that incident — treat them as reference/inspection tools only, don't extend the pattern of rewriting scene/prefab JSON.
- Treat prefabs and scenes as editor-owned black boxes. Structural changes (adding nodes/components, wiring references) belong in the Cocos Creator editor; TypeScript should only be defensive against missing/null references (nodes not found, components not assigned), never assume it can patch the hierarchy itself.
- Any polling/retry loop that waits on another singleton becoming ready (e.g. via `scheduleOnce`) must have a bounded retry count or timeout. An unbounded retry previously caused a stack overflow that froze the editor.
- Don't assert exact Cocos Creator 3.8.8 UI/menu names or steps from memory (e.g. component naming, menu placement) without checking — a prior wrong claim about the "Raw Image" component wasted debugging time.

## Architecture

**Single-scene, prefab-swapped screens.** The project uses one Cocos scene (`scene-Main`); "screens" (Title, Home, Ingame) are Prefabs instantiated/destroyed by `GameManager.switchContent()` rather than separate Cocos scenes. UI prefabs (Title/Home) are added under the `Canvas` node (screen space); the Ingame prefab is added at the Scene root (world space, since gameplay uses a 3D player model). `switchContent()` also handles camera bookkeeping — enabling/disabling scene vs. UI cameras and creating a fallback camera if a prefab doesn't ship one.

**Singleton pattern.** `GameManager`, `UIManager`, `SoundManager`, `GameDatabase` are Components with a `static instance` set in `onLoad()`, guarded against duplicate instances and against a special "Dummy" placeholder node that can be hijacked (see the `instance.node.name.includes("Dummy")` checks). `DataManager` is a plain (non-Component) lazy singleton. Follow this same guard pattern for any new manager singleton.

**`GameManager`** (`assets/scripts/GameManager.ts`) is the central orchestrator: owns `GameState` (Title/Home/Ingame/Result/Failure, defined in `Constants.ts`), drives the enemy spawn timer and mission-distance countdown in `update()`, and exposes the bullet/item/damage-text/explosion "factory" methods that `PlayerController`, `Enemy`, and `Bullet` call into. Cross-component consumers depend on the `IGameManager` interface in `Constants.ts` (not the concrete class) to avoid circular imports — extend that interface when adding new cross-cutting `GameManager` APIs.

**Data pipeline (two layers):**
- `GameBalanceData.ts` — auto-generated flat constants from `../game_balance.xlsm` (weapons, physics, player base stats). `Constants.ts` merges this into `GAME_SETTINGS`, adding code-only tuning values on top.
- `GameDatabase` (`assets/scripts/GameDatabase.ts`) — loads CSV `TextAsset`s (`assets/resources/Excels/*.csv` — moved here from `assets/Excels/*.csv` so `resources.load()` fallback paths can resolve them; edited via the `Extension > Master Manager` editor panel, `extensions/master-manager/`) through `CSVHelper.parse()` into typed rows (`GameDataTypes.ts`), then cross-links them by ID at parse time so runtime code never re-joins tables. Enemy prefabs are matched by name against the CSV's `PrefabName` column (prefabs are bulk-loaded from `resources/Prefabs/Enemy` via `resources.loadDir`, not assigned individually in the Inspector).

**Player is 2D logic + 3D visuals.** `PlayerController` moves/collides in 2D screen space (mouse/touch-follow with lerp, Y-position-based speed zones), but a 3D glTF model (`PlayerShip_3D` prefab) is attached as a child at runtime (`GameManager.resolveInGameReferences`) purely for rendering; banking/roll is faked by rotating that child model based on frame-to-frame X movement.

**`SoundManager`** runs a 3-source BGM pool for crossfading, per-group SE polyphony/cooldown/priority (groups: Player/Enemy/System, tuned via `Sounds.csv`), and manual distance-based volume falloff for "3D" SFX (`play3dSE`) — there's no engine audio spatializer involved. It queues any BGM/SE requests that arrive before `GameDatabase.isReady` and flushes them once the database finishes loading.

**`DataManager`** persists one JSON blob to `sys.localStorage` under `SAVE_KEY` (`Constants.ts`). `load()` deep-merges saved data over `getInitialData()` defaults so old saves gain new fields without migration code.

**`enginePatches.ts`** must stay imported first (for its side effects) in `GameManager.ts` — it monkey-patches `Sprite.prototype` to guard against an editor-preview-only null `_uiProps` crash.
